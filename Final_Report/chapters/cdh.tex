\chapter{Command and Data Handling (CDH)}

\section{Responsibilities}

CDH is the sensor-acquisition and data-management layer of the flight
software. Once per 1~Hz major cycle it reads every sensor on the platform,
condenses the results into a single shared data structure -- the
\emph{datapool} -- and hands that snapshot to the rest of the flight
software (FSW, FDIR, TT\&C, and SD logging) to consume. Its
responsibilities are:

\begin{itemize}[nosep]
  \item \textbf{Sensor acquisition.} Drive the GPS (u-blox MAX-M10S), the
        IMU (MPU-6050), the barometer (MS5607), and the EPS battery-voltage
        monitor, each through a dedicated equipment handler.
  \item \textbf{Datapool ownership.} Be the sole writer of the
        \texttt{SensorData\_t} datapool: every field is (re)written once per
        tick so that all downstream consumers read one internally consistent
        snapshot (Section~\ref{sec:cdh-datapool}).
  \item \textbf{Data validation.} Range-, plausibility-, and timeout-check
        every sensor stream, and publish a per-sensor \texttt{*\_valid} flag
        so consumers never act on stale or impossible data
        (Section~\ref{sec:cdh-validation}).
  \item \textbf{Shared-bus ownership.} Own the I2C1 hardware that the
        environmental sensors share, and execute the multi-tick bus-restart
        sequence when FDIR requests recovery -- CDH is the sole writer of
        \texttt{i2c\_bus\_state}.
  \item \textbf{Payload ingest.} Timestamp and copy the Coral payload status
        block into the datapool, since the payload has no clock of its own.
\end{itemize}

\section{Interfaces}

The primary interface CDH exposes is not a bus but a data structure. CDH is
a producer: it turns raw peripheral traffic into the datapool, and every
other subsystem is a consumer of that datapool (Table~\ref{tab:cdh-flow}).
The GPS, IMU, and barometer share a single I2C bus that CDH owns; the
battery pack voltage is read on an ADC input from the EPS telemetry divider
(IF-008, described in the EPS chapter). The overall software structure --
equipment handlers feeding the datapool, and the datapool feeding every
other subsystem -- is shown in Figure~\ref{fig:cdh-architecture}.

The entry points are deliberately narrow. \texttt{CDH\_Init()} brings up
every handler once before the superloop starts and records the ground
pressure baseline; \texttt{CDH\_Update(dp, scv)} runs the entire
acquire-validate-publish cycle for one tick; and
\texttt{CDH\_RequestBusRestart()} is the single call FDIR uses to ask CDH to
recover the I2C bus.

\section{Design Decisions}

\subsection{The Datapool}
\label{sec:cdh-datapool}

All inter-subsystem state lives in one packed structure,
\texttt{SensorData\_t}, defined once in the interface-control header
(\texttt{datapool.h}) and shared as the single global \texttt{g\_datapool}.
Rather than have each subsystem poll sensors on its own schedule, CDH
writes the whole structure once per cycle and everyone else reads it. The
structure is grouped by source, and every sensor group carries its own
validity flag (Table~\ref{tab:cdh-datapool}).

Three decisions define the datapool contract. First, \textbf{one writer}:
only \texttt{CDH\_Update} writes \texttt{g\_datapool}, which removes any
need for locking in the single-threaded superloop and guarantees a
consistent snapshot. Second, \textbf{validity is explicit}: a sensor that
fails a check has its group's \texttt{*\_valid} flag cleared while the last
values are left in place, so a consumer that honours the flag degrades
gracefully and one that ignores it at least sees the last good reading
rather than a zero. Third, \textbf{raw units}: fields are stored in source
units (degrees, g, Pa, mV) and engineering conversions are pushed to the
ground station, keeping the flight CPU free of unnecessary floating-point
formatting -- the same philosophy the telemetry packet follows.

structure is declared \texttt{\_\_attribute\_\_((packed))}, so it carries no
padding and its 98-byte size is exactly the sum of its fields -- which
matters because those fields feed straight into the downlink telemetry
packet and the SD housekeeping row with no repacking.

Alongside the volatile datapool, CDH contributes to the \texttt{SCV\_t}
(spacecraft configuration vector), the 33-byte structure that FSW/FDIR
persist to flash across resets. CDH updates its health-related fields
(equipment fault flags, the last battery reading) each cycle while FSW/FDIR
own flight phase and reset bookkeeping.

\textbf{Memory footprint.} The datapool is deliberately small enough to be
irrelevant to the memory budget of the platform's STM32L476RG
(Table~\ref{tab:cdh-memory}). The live datapool and its persistent shadow
together occupy 131~B of the 128~KB SRAM -- under 0.1\,\%; even the full
downlink packet that re-serializes them adds only $\sim$155~B. Storing raw
fixed-width types rather than expanded engineering structures keeps it that
way; the platform's real SRAM pressure comes from the payload image frame
(streamed in 512-byte chunks, never buffered whole), not from housekeeping
state. The persistent \texttt{SCV\_t} is written to the last 2~KB flash page
at \texttt{0x080FF800}, at the very top of the 1~MB flash and clear of the
firmware image, with a magic word and CRC-16 so a blank or corrupt page is
detected on boot.

\subsection{Non-Volatile Datapool Backup}
\label{sec:cdh-nvm}

The SD card holds the primary housekeeping record, but a card may be absent,
develop filesystem corruption, or cease to acknowledge on the SPI bus. To
retain a recoverable flight history under any of these failures, CDH mirrors
the datapool into the microcontroller's internal flash over a data path that is
fully independent of the SD subsystem: the write engages only the CPU and the
on-chip flash controller -- no SPI transaction and no removable media -- so a
usable record persists even when the SD path is inoperative. The datapool is
stored unfiltered, so each record additionally preserves the fault condition
itself: the cleared validity flags and the \texttt{timestamp\_ms} that CDH
writes at the head of every cycle irrespective of sensor health.

\textbf{Flash budget.} The store occupies a reserved 80~KB region -- 40 of the
device's 2~KB flash pages -- at the top of the 1~MB flash, immediately below
the 2~KB SCV page. Both regions are excluded from the firmware image by
reducing the usable flash declared to the linker to 942~KB
(\texttt{STM32L476RGTX\_FLASH.ld}), so the linker cannot place code or
constants within them. The allocation is conservative: the linked image
measures approximately 109~KB, roughly one-ninth of the available flash,
leaving the backup region separated from the image by more than 800~KB of
unused flash (Table~\ref{tab:cdh-nvm-budget}).

\begin{table}[H]
\centering

\toprule

\textbf{Storage scheme.} The region is operated as a circular log of fixed
104-byte records, each comprising a 16-bit magic word, a 16-bit sequence
number, the 98-byte datapool, and a CRC-16; nineteen records occupy each 2~KB
page. One record is appended every 30~s. A page is erased exactly once per lap
of the ring -- when the write cursor first enters it -- so the cost is one
erase per page per lap rather than one erase per record, the same wear-limiting
strategy employed by the SCV store. Record ordering and write-position recovery
rely on the sequence number rather than the datapool timestamp, because
\texttt{HAL\_GetTick()} is reset to zero at every boot, whereas the recorder is
required to remain coherent across precisely those resets.

\textbf{Interval and capacity.} At a 30~s interval the 760 available slots span
6.3~h; the complete six-hour flight therefore fits within a single lap with
margin, and no data is lost even should the SD card fail at lift-off. A longer
flight wraps and retains the most recent 6.3~h, and the worst-case loss
following an unclean reset is bounded to one 30~s interval. As one lap
corresponds to approximately one flight, each page is erased on the order of
once per flight, yielding of order $10^{4}$ flights against the guaranteed
flash erase endurance; endurance is therefore not a constraint at this rate.
The interval trades flash capacity against temporal resolution: the identical
scheme requires 128~KB at a 20~s interval, or 40~KB at 60~s.

\textbf{Retrieval.} The record is recovered through the ST-Link debug interface
integral to the Nucleo board, without removable media. A memory read of the
reserved range (for example
\texttt{STM32\_Programmer\_CLI -r 0x080EB800 0x14000 dump.bin}) transfers the
region to a host file, after which an offline utility traverses it in 104-byte
records, retains those bearing a valid magic word and CRC, and orders them by
sequence number to reconstruct the flight time-line.

\subsection{Equipment Handler Pattern}
\label{sec:cdh-handlers}

Each sensor is wrapped in an \emph{equipment handler} that follows one
uniform value-semantics pattern:

\begin{lstlisting}[language=C]
Handler H_Init(bus);              /* construct + first read      */
H = H_Update(H, bus);             /* re-read, returns new state  */
\end{lstlisting}

The handler struct carries everything that sensor needs to manage itself:
its latest reading, its previous reading, a local health flag, and the
timestamps that drive its cadence. Passing the handler by value in and out
of \texttt{Update} makes each sensor's state self-contained and its update a
pure state transition, which keeps \texttt{CDH\_Update} a flat, readable
sequence of calls with no hidden global sensor state. Each handler also
owns its own \emph{rate}: the 1~Hz major cycle is the outer clock, but a
handler may sample faster or run an availability check on its own interval
(Table~\ref{tab:cdh-handlers}).

\begin{table}[H]
\centering
\begin{tabular}{llll}
\toprule
\textbf{Handler} & \textbf{Device} & \textbf{Read rate} & \textbf{Health check} \\
\midrule
GPS       & u-blox MAX-M10S & 1~Hz (on new message) & fix + timeout \\
IMU       & MPU-6050        & 10~Hz (100~ms)        & 0.5~Hz presence + flatline \\
Barometer & MS5607          & 2~Hz (500~ms)         & 0.5~Hz presence \\
EPS       & battery divider & 1~Hz                  & conversion success \\
\bottomrule
\end{tabular}
\caption{Equipment handlers and their internal cadences.}
\label{tab:cdh-handlers}
\end{table}

\textbf{GPS (MAX-M10S).} The receiver is driven over I2C in u-blox's native
UBX binary protocol rather than NMEA text. At start-up the handler
configures the module through the M10 configuration interface
(UBX-CFG-VALSET, RAM layer): it enables UBX output on I2C, disables the
NMEA protocol, requests the \texttt{NAV-PVT} navigation solution at 1~Hz,
and selects the \emph{Airborne $<$1\,g} dynamic model so the navigation
filter does not clamp the rapid altitude changes of flight. Each 100-byte
\texttt{NAV-PVT} message delivers position, ellipsoidal and mean-sea-level
altitude, the three velocity components, ground speed, heading, fix type,
satellite count, and per-solution accuracy estimates in a single
checksum-protected frame -- replacing the multi-sentence NMEA parse with
one binary decode and giving the FSW a directly usable vertical velocity.
The binary path also fixed a latent driver bug: the u-blox
bytes-available register is 16~bit (\texttt{0xFD}/\texttt{0xFE}), and
reading only the high byte -- which the earlier NMEA driver did -- returns
the pending count divided by~256 and starves the comparatively low-rate
UBX stream.

\textbf{IMU (MPU-6050).} Sampled at 10~Hz so the FSW sees acceleration
well above the 1~Hz cycle rate; the handler also runs a slow presence check
and a flatline detector that flags the sensor if its output stops changing.

\textbf{Barometer (MS5607).} Sampled at 2~Hz. At initialization the handler
captures the ground pressure and altitude as a baseline, so
\texttt{baro\_alt\_m} is reported as height above the launch site rather
than absolute pressure altitude.

\textbf{EPS battery monitor.} The battery pack voltage is read on an ADC
input through the EPS telemetry divider (22\,k$\Omega$ high side,
10\,k$\Omega$ low side, IF-008): the ADC sees
$V_\text{pack}\times R_\text{low}/(R_\text{high}+R_\text{low}) =
V_\text{pack}\times0.3125$, which the firmware scales back by the
$3.2\times$ multiplier to recover the pack voltage in millivolts and store
it as \texttt{batt\_voltage\_mv}. The two-cell parallel pack spans
3.0--4.2~V (see the EPS chapter), so the divider output stays near 1.3~V,
well within the 3.3~V ADC range, and the chain meets the 5\% telemetry
accuracy of IF-008.

\subsection{Sensor Validation and Fault Handling}
\label{sec:cdh-validation}

Validation is layered. Each handler catches faults local to its own device
-- a GPS with no fix, an IMU whose output has flatlined, a barometer that
fails to acknowledge on the bus. On top of that, a central validation pass
(\texttt{SensorValidation\_Update}) runs every cycle after all handlers
have reported and applies cross-checks that need the assembled datapool:

\begin{itemize}[nosep]
  \item \textbf{Barometer.} Reject non-physical pressure
        ($<0$ or $>1519$~hPa) or temperature ($<-100$\,\textdegree C).
  \item \textbf{GPS.} Require a non-zero fix; reject altitude outside
        $0$--$40$~km; reject a solution more than 1000~km from the launch
        site (a coarse geofence around Munich); and declare the receiver
        stale if no new fix arrives for 60~s.
  \item \textbf{IMU.} Declare the sensor failed if the acceleration
        magnitude stays below the flatline threshold for longer than 4~s.
\end{itemize}

A failed check clears the datapool validity flag for that group and
increments a persistent fault counter, but leaves the last values in place.
Recovery is graded by how many sensors are affected. A \emph{single} failed
sensor triggers a recovery attempt that is then retried no more than once
per 60~s, avoiding a tight retry loop that would starve the rest of the
cycle. \emph{Multiple} simultaneous sensor failures are read as a
shared-bus problem rather than independent device faults, so validation
calls \texttt{CDH\_RequestBusRestart()}; because CDH owns the I2C hardware,
it -- not the validation code -- carries out the restart across subsequent
ticks and republishes \texttt{i2c\_bus\_state}. The whole scheme is
fail-soft: a degraded sensor removes its own data from the solution without
ever stalling the 1~Hz cycle or the subsystems downstream of it.
