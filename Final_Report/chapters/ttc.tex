\chapter{Telemetry, Tracking and Command (TT\&C)}

\newcommand{\ttcfield}[1]{{\ttfamily\footnotesize\detokenize{#1}}}

\section{Subsystem Overview}

The Telemetry, Tracking and Command (TT\&C) subsystem is the operational link
between Lakitu and its ground crew. It periodically downlinks the current
spacecraft state, provides the GNSS information used to track and recover the
balloon payload, accepts a small set of uplink messages, and exposes radio
health to Fault Detection, Isolation and Recovery (FDIR). The implemented link
is bidirectional half-duplex LoRa using an RFM95W/SX1276-class modem at
869.525~MHz. The flight computer is an STM32L476RG and the ground radio is driven
from a PC through a CH347 USB-to-SPI adapter.

The complete end-to-end system is shown in Figure~\ref{fig:ttc-architecture}.
An important design boundary is that FSW owns flight phase and system state,
while the TT\&C packet builder encodes those shared values and TT\&C owns radio
scheduling, delivery attempts, acknowledgement handling and modem health.
FDIR, rather than TT\&C, owns the
policy that decides when a radio failure is severe enough to request recovery.

\subsection{Responsibilities}

The implemented subsystem configures and verifies the modem, maintains
continuous receive outside transmissions, schedules a nominal frame every
20~s and on change of flight state, and transmits without blocking the spacecraft
superloop. It retains an unacknowledged frame and retries the exact same bytes,
sequence and CRC up to three total attempts. It also parses acknowledgements
and commands, rejects malformed or replayed traffic, exposes raw health to
FDIR, and executes asynchronous isolation and recovery actions.

On the ground, TT\&C receives and validates frames, restores engineering units,
records link metadata and events, acknowledges valid downlinks, and provides
live and historical data to the operator dashboard. Tracking is not a separate
RF ranging function: it comes from the GNSS latitude, longitude, altitude,
speed, course and time carried in every telemetry frame.

\section{Link Budget, Airtime and Channel Use}
\label{sec:ttc-link-budget}

The link-budget assumptions use 35~km altitude and 120~km horizontal drift,
giving 125~km slant range. Free-space path loss is
\begin{equation}
L_{\mathrm{FS}} = 32.44 + 20\log_{10}(d_{\mathrm{km}})
                 + 20\log_{10}(f_{\mathrm{MHz}}),
\end{equation}
which gives 133.17~dB at 125~km and 869.525~MHz. Source review confirms that
both endpoints now use +17~dBm conducted output. For the 862--1020~MHz band,
the RFM95W/SX1276 data-sheet sensitivity at SF8/BW125 is approximately
$-126$~dBm, giving a 143~dB transmitter-to-sensitivity span before antennas and
propagation losses. Retaining the existing antenna, cable, atmospheric and
polarization assumptions gives Table~\ref{tab:ttc-link-budget}.

The symmetric +17~dBm configuration makes the modeled downlink and uplink
margins equal. Both exceed the 10~dB targets in MR-004, PR-004 and PR-007, and
the modeled raw and processed SNR values exceed the corresponding PR-007
thresholds. This is analytical evidence, not RF qualification: acceptance still
requires measured sensitivity, characterized installed antennas and cables,
confirmed ground-antenna gain, and representative bidirectional range testing.

At SF8, BW125, CR~4/5, explicit header, CRC and an eight-symbol programmed
preamble, symbol time is 2.048~ms. A 92-byte frame uses 128 payload symbols and
has 287.232~ms total airtime. The packet carries $92\times8/20=36.8$ payload
bit/s, 1.18\% of the nominal 3125~bit/s LoRa rate, but that ratio is not channel
occupancy. At a strict 20~s period, one flight transmission uses
\begin{equation}
\frac{0.287232}{20}\times100\% \approx 1.44\%.
\end{equation}
Three attempts of the retained frame occupy about 4.31\% of the same interval.
Those values are below the selected requirement's 10\% alternative, but the
final compliance record must measure aggregate occupancy separately for each
transmitter and include event packets, retries, ground ACKs and commands. It
must also confirm the applicable spectrum-access basis, ERP, equipment
conformity and balloon/national authorization.

The RFM95W is connected to STM32 SPI1 in master mode. Transfers are full
duplex, 8-bit and interrupt driven. Chip select and reset are ordinary GPIOs;
the driver polls the modem IRQ register, so the implemented path does not need
a DIO interrupt line.

\section{Telemetry Generation and Scheduling}

The superloop calls \ttcfield{TTC_Service()} on every iteration because TT\&C
and the LoRa driver are cooperative, non-blocking state machines. They advance
at most a small SPI or state step per call, allowing FDIR and the independent
watchdog to continue while a radio operation is in progress.

When \ttcfield{TTC_TelemetryDue()} is true, the main loop calls
\ttcfield{TTC_BuildTelemetryPacket()} with the 1~Hz
sensor datapool, persistent Spacecraft Vector (SCV), and volatile TT\&C
health/command snapshots. A frame is due before the first transmission, after
20~s from the last successful TX, or when an immediate request is latched.
Flight-phase changes and received commands set this latch. If a previous frame
still awaits its ACK, no new frame is built: the pending sequence is completed
or abandoned first.

LoRa supplies the radio packet, while reliability is implemented at the
application layer. Figure~\ref{fig:ttc-reliability} summarizes a transaction.

After \textit{TxDone}, flight returns to continuous RX and waits 5~s for an
authenticated ACK containing the packet's boot count, sequence number and
transmit uptime. All three identifiers must match the outstanding frame before
it is released, preventing replay of a
captured ACK after a reboot or sequence wrap. The last accepted ACK is
classified as duplicate; another valid tuple is unexpected. ACKs require no
ACK-of-ACK. Ground sends the ACK only after full application validation, waits
3.0~s so flight can process \textit{TxDone} and restore continuous RX, and
then restores its own continuous RX after the ACK attempt. It acknowledges a
duplicated sequence again. A duplicate normally means downlink succeeded but
the earlier ground ACK did not reach flight in time.

Command IDs are non-zero 16-bit values. A command is accepted once, an executed
ID is reported as \texttt{DUPLICATE}, and an ID older than the replay window is
reported as \texttt{STALE} rather than successful. Ground persists the next ID
across backend restarts, serializes command transactions, and accepts a response
only from telemetry newer than the pre-command baseline. It retries up to three
times with a 5~s radio-TX timeout and a 25~s flight-response timeout. New
commands and command-triggered responses are limited to the nominal 20~s
telemetry cadence. The ground API additionally provides one-shot command
arming, rate limiting, and operator-token enforcement for non-loopback
operation. \texttt{REQ\_TELEMETRY} is currently the only operational verb.
Ground never wraps the 16-bit ID space under one RF key; exhaustion requires
coordinated rekeying, preventing captured commands from becoming valid again
after an ID wrap. Unauthenticated packets are ignored without mutating the
trusted command or ACK latches.

\section{Ground Segment}

The ground segment has three layers. Python controls an RFM95W through CH347,
reads payload/RSSI/SNR/CRC, and restores continuous RX after transmissions.
FastAPI validates and decodes v8, tracks lost/duplicate sequences, keeps bounded
history, persists uplink IDs, retains rejected-frame observations, writes
telemetry and event CSVs, exposes REST, and broadcasts a consistent status
envelope over WebSocket. The React dashboard provides Overview, Health, Position/Flight
Phase, Link Analytics, Commands and Raw Telemetry views. Its live-data hook
batches rapid updates, merges initial history with WebSocket traffic and keeps
duplicate packets and ground events visible without replacing the latest valid
spacecraft state.

Invalid-length, unsupported-envelope and physical-CRC observations remain
available for diagnosis but never replace the latest valid spacecraft state.
RSSI packet power includes negative SNR as required by the SX1276 measurement
model; flight and ground both enable and verify the same HF LNA-boost setting.
