\chapter{On-Board Computer (OBC)}

\section{Responsibilities}

The OBC is the single flight computer of the platform: one microcontroller
hosts all subsystem software -- CDH sensor acquisition, the FSW state
machine, FDIR monitoring, TT\&C packetization, and SD-card logging -- with
the Coral payload as the only other processor on board. Its
responsibilities are:

\begin{itemize}
  \item \textbf{Compute platform.} Execute all flight software in a fixed
        1~Hz major cycle (\texttt{CDH\_Update} $\rightarrow$
        \texttt{FSW\_Update} $\rightarrow$ \texttt{FDIR\_Update} $\rightarrow$
        SD logging $\rightarrow$ TT\&C service).
  \item \textbf{Timekeeping.} Provide the mission time base
        (\texttt{HAL\_GetTick()}); the Coral has no RTC, so the OBC
        timestamps every payload packet.
  \item \textbf{Mass storage.} Archive housekeeping telemetry and payload
        image frames to the SD card (FR-016/FR-017, Section~\ref{sec:obc-sd}).
  \item \textbf{Platform health.} Run the independent watchdog (FR-011),
        classify reset causes into the SCV, and digitize battery voltage
        from the EPS divider (IF-008).
\end{itemize}

\section{Design Decisions}

\textbf{Hardware selection.} Three candidate boards were evaluated
against form factor, power consumption, and mechanical fit inside the 1U
enclosure (Table~\ref{tab:obc-tradeoff}). All three meet the 80~MHz
minimum clock requirement (PR-005); the differences are in power and
mechanics. The Nucleo-144 H753ZI, although lab-supplied, is too long for
the 1U stack and would only fit after snapping off its ST-Link section --
a destructive modification that also removes the on-board debugger. The
F401RE fits and would work, but the L476RG delivers the same 80~MHz at
roughly half the core current, so at equal price and identical form
factor the more efficient part won.

The selected STM32L476RG (Cortex-M4 at 80~MHz, 1~MB flash, 128~KB SRAM)
comes from ST's ultra-low-power line, purpose-built for battery
operation: the 1~Hz control problem does not need more compute, and the
low-power core keeps the OBC's share of the EPS budget small
($\sim$0.4~W including sensors and LoRa). Its memory provides roughly
5$\times$ the headroom the flight software was expected to need
(bounded by the 80\% flash/RAM ceiling of PR-008). The Nucleo-64 format
retains the on-board ST-Link debugger, so programming and debug need
nothing but a USB cable, and its breakout headers suit the hand-wired
integration. The choice imposes two constraints that shaped the
software: a 50~KB payload frame occupies 39\% of SRAM, so images can
never be buffered whole; and the Nucleo-64 has no SD slot or SDMMC
wiring, so the SD card runs over SPI.

\textbf{Superloop instead of an RTOS.} All software runs in a single
bare-metal loop with a fixed call order and no preemption. With one
1~Hz rate group and no hard concurrent deadlines, an RTOS would add
stack-per-task RAM cost and priority/locking failure modes without buying
anything; the superloop makes timing trivially auditable. The independent
watchdog (IWDG) is refreshed exactly once per loop iteration with a
timeout below the 10~s FR-011 limit, so any hang anywhere in the cycle
ends in a clean reset rather than a silent loss of the mission. A
FreeRTOS port was scoped in the design phase as a stretch goal for
comparison only; the FSM superloop was always the committed flight
build, and the port was dropped without mission impact.

\textbf{Boot order and degraded boot.} FDIR initializes first, before any
peripheral driver, so reset classification and the watchdog-reset counter
run even if later initialization fails. Each subsystem init is gated on
its SCV equipment flag: a peripheral that fails to start is flagged
faulty and the boot continues -- the OBC always comes up, in a degraded
mode if necessary, rather than hanging in an init retry loop. The
boot-time battery-voltage guard (EPS chapter) is checked before normal
operation resumes. The staged escalation this gating implements after
repeated watchdog resets is detailed in the Flight Software chapter
(Section~\ref{sec:fsw-reduced-mode}).

\subsection{SD Card Storage}
\label{sec:obc-sd}

The SD card holds the two on-board data products: a 1~Hz housekeeping log
(FR-016) and the payload image archive, keyed by the payload sequence
number \texttt{SEQ} so each downlinked cloud fraction can be matched to
its source frame post-flight. The stack is a bare-metal SD-SPI driver
under FatFs (Figure~\ref{fig:obc-sd}): card initialization is clocked at
312.5~kHz to respect the sub-400~kHz SD specification window, then raised
to 10~MHz for operation.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{obc_sd_pipeline.png}
  \caption{SD storage pipeline, file lifecycle, and fault ladder.}
  \label{fig:obc-sd}
\end{figure}

\textbf{Housekeeping log.} Each 1~Hz cycle appends one 46-column CSV row:
the full datapool snapshot (GPS, IMU, barometer, battery, the 16-byte
Coral status block) plus the complete SCV, all scaled to integers on
write so the log needs no floating-point formatting and parses
unambiguously. Three choices bound the damage any single failure can do:

\begin{itemize}
  \item \textbf{One file per minute.} The log rotates every 60~s, so a
        corrupted file costs at most one minute of data.
  \item \textbf{Sync every row.} \texttt{f\_sync} runs after each record;
        power loss loses at most the row being written.
  \item \textbf{Self-identifying files.} A file is created as
        \texttt{LOG\_<session>\_START\_<t>\_OPEN.CSV} and renamed on clean
        close to carry its end time and duration -- any file still named
        \texttt{\_OPEN} after the flight is known to have died mid-write.
        Session numbers are recovered by directory scan, so numbering
        survives reboots without persistent state.
\end{itemize}

\textbf{Image archive.} Payload frames arrive on UART5 as 50\,196-byte
CRC-16-protected packets and are streamed to one file per frame
(\texttt{F<SEQ8>.RAW}) through a 512-byte chunk buffer -- at no point is
a whole frame held in RAM, which the 128~KB SRAM budget rules out. A
failed CRC or a write error drops that frame only; the next \texttt{SEQ}
starts a fresh file.

\textbf{Fault handling.} Any FatFs error closes the file, unmounts the
volume, sets the SD bit in \texttt{equipment\_faults}, and schedules a
retry 5~s later; after three consecutive faults the SPI driver is fully
re-initialized from scratch. The card is declared healthy again only
after a completed write-and-sync, not merely a successful mount. The
entire SD path is deliberately fail-soft: telemetry reaches the ground
over LoRa regardless of card state, so losing the SD card loses the image
training archive, never the science result or the flight.
